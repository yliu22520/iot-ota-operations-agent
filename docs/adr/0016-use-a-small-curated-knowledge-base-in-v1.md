# 第一版使用小型自建运维知识库

第一版固定使用 8 篇自建资料，覆盖 OTA 状态、版本兼容、回调超时、下载与校验、设备离线与资源不足、重试安全策略和 2 篇历史故障案例，作为辅助知识参与诊断解释；知识库不阻塞结构化工具链，也不能覆盖权威规则或直接决定重试资格。向量由 Spring AI 本地 ONNX `intfloat/multilingual-e5-small` 生成，使用 384 维 pgvector 余弦检索，不依赖 provider-neutral ONNX embedding、第二个云端密钥、GPU 或 Ollama。选择小型、可控的资料集，是为了验证检索与证据引用的价值，同时避免 Elasticsearch 等重型基础设施成为项目主体。

## Considered Options

- 第一版完全不做知识检索
- 一开始建设大规模文档检索平台
- 使用 5～10 篇可控资料作为辅助知识（选择）

## Consequences

- 每篇 Markdown 通过 Front Matter 声明 `documentId`、版本、类型、状态、适用组件和更新时间，只有 `ACTIVE` 文档进入索引。
- 文档按 Markdown 标题和段落切成约 300～500 Token 的块，并保留约 50 Token 重叠以及文档、章节、版本和内容哈希元数据。
- 查询先进行元数据过滤，再执行 Top‑4 余弦检索；相似度阈值由项目案例校准，不凭经验写死。
- 索引按内容哈希幂等更新；报告引用文档、章节和块 ID，评测验证引用是否正确而不只是检索命中。
- 15 个评测案例至少覆盖正确引用、过期文档排除、无相关资料、检索失败和伪造引用拒绝五类断言。
- ONNX 模型版本和 SHA-256 必须固定，模型不进入 Git；Docker 构建阶段下载并缓存，运行时不依赖外部模型仓库。
- 后续扩展资料量时，可以替换存储实现而不改变权威规则接口。
